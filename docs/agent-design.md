# Агент TasteShift: решение и проверка подхода

4 октября 2026. Исследование официальной документации и небольшой исполняемый эксперимент. После исследования первая интеграция подключена к API приложения; фактический объём и ограничения описаны в [отчёте внедрения](agent-implementation.md). Ниже сохраняется целевой план. Живые Qloo и LLM не проверялись: ключа Qloo пока нет.

## Решение

Предлагаю один агент на **Pydantic AI**, встроенный в Python backend. Его работа — превращать намерение человека в подборку и небольшой план знакомства с новым: выбирать разрешённые инструменты, замечать нехватку данных, связывать разные категории. Источник сущностей — Qloo. Исключения, ранжирование, допустимые ID и сохранение результата — обычный Python-код.

Это уточнение прежнего решения о собственном ограниченном цикле. Границы остаются прежними, но цикл вызовов и проверку формы ответа берём из библиотеки. Выбор — инженерный вывод для нашего проекта, а не результат сравнительного бенчмарка фреймворков.

## Какие варианты рассмотрены

| Вариант | Что даёт | Решение для TasteShift |
| --- | --- | --- |
| Pydantic AI | Типизированные зависимости, инструменты, выходные схемы и валидаторы | Выбираем: backend уже использует Pydantic; удобно проверять ответ относительно данных конкретного запуска |
| OpenAI Agents SDK | Готовый цикл, function tools, guardrails, sessions, tracing | Рабочая альтернатива; сейчас нет причины переносить контракты и память в ещё один слой |
| LangGraph | Состояние графа, checkpoints, продолжение прерванной работы | Вернуться, если появятся длинные задания с паузами и подтверждениями; текущая подборка укладывается в один запрос |
| Собственный цикл | Полный контроль над протоколом | Резервный вариант; самостоятельно поддерживать dispatch, retry и завершение сейчас невыгодно |

Возможности библиотек: [Pydantic AI Agents](https://pydantic.dev/docs/ai/core-concepts/agent/), [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/), [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence). OpenAI SDK также поддерживает не только OpenAI-модели; выбор выше не основан на предположении о жёсткой привязке к одному провайдеру.

Не делаем отдельных «исследователя», «критика» и «куратора» только ради демонстрации нескольких агентов. Для первого сценария достаточно одного принимающего решения агента и независимых проверок его результата.

## Пользовательский сценарий

Человек подтверждает 3–5 интересов и пишет, например: «Хочу спокойный вечер, но не ещё один похожий фильм».

Агент выбирает подходящий порядок действий: получить фильмы и музыку, при необходимости запросить дополнительную категорию, затем составить план из полученных сущностей. Для MVP поддерживаем исполнителей, фильмы и книги. Рестораны, маршруты и доступность событий не обещаем без соответствующей интеграции.

Результат может выглядеть как «начни с этого исполнителя, затем посмотри этот фильм». Все названия и ссылки подставляет сервер из проверенных данных. Сам порядок знакомства — предложение агента, а не утверждение Qloo о том, что эти две сущности связаны друг с другом.

«Спокойный» и «на вечер» — мягкие пожелания, если провайдер не даёт проверяемых признаков. Длительность фильма, наличие на стриминге, язык книги и возрастной рейтинг нельзя выдумывать. Жёсткое требование с неизвестным значением приводит к уточнению или сообщению о недостаточном покрытии, а не к молчаливому ослаблению.

## Разделение ответственности

```text
HTTP-запрос + подтверждённые интересы + явные реакции
    → DiscoveryService: сессия, ограничения, бюджет запуска
    → AgentRunner: намерение и выбор разрешённых шагов
        ↔ инструменты: QlooClient → нормализованные кандидаты и evidence
        ↔ RankingService: допустимый ранжированный shortlist
    → OutputValidator: ID, evidence, ограничения, отсутствие дублей
    → серверная сборка ответа и сохранение снимка
```

Qloo определяет исходный набор культурных рекомендаций. RankingService отвечает за Safe → Wild, исключения и разнообразие. Агент работает только с shortlist, адаптирует план к намерению и может запросить дополнительный разрешённый набор. Он не меняет веса ранжирования и не возвращает отклонённые сущности через другую категорию.

В первом шаге реализации стоит вынести организацию подборки из `main.py` в `DiscoveryService`. Не нужно одновременно переписывать уже проверенный QlooClient или алгоритм ранжирования.

## Инструменты

| Инструмент | Аргументы модели | Ограничения сервера |
| --- | --- | --- |
| `get_candidates` | Категория из enum | Интересы и исключения берутся из контекста; один исходный запрос на категорию, повтор разрешён только с изменением допустимых параметров |
| `get_shortlist` | Набор уже полученных ID | Проверка принадлежности запуску, затем существующее ранжирование |
| `get_details` | ID из текущего набора | Пакетный запрос к Qloo; без произвольных URL и ID из других сессий |

Не даём модели инструменты SQL, shell, произвольный HTTP или запись реакций. Реакцию сохраняет только пользовательский запрос. Сохранение окончательной подборки делает сервис после проверки, а не модель.

Контекст запуска содержит подтверждённые интересы, исключения, разрешённые категории, level, полученные кандидаты, evidence и счётчики. Секреты, cookie, идентификатор чужой сессии и API-ключ не становятся аргументами инструментов или частью prompt. Реестр полученных данных принадлежит одному запуску; глобальным может быть определение агента, но не его изменяемый контекст.

## Контракт ответа и доказательства

Целевой результат — одно из трёх состояний: `ExperiencePlan`, `NeedsClarification`, `InsufficientCoverage`. План содержит ID выбранных сущностей, evidence ID и шаги знакомства. Уточнение — один конкретный вопрос. Недостаточное покрытие — доступная часть результата и перечень неподтверждённых требований.

Валидатор проверяет не только JSON-схему:

- каждый ID получен в этом запуске и входит в разрешённый shortlist;
- отклонённые, уже известные и повторяющиеся сущности исключены;
- evidence существует и относится к указанной сущности;
- поля ограничены по длине, enum и количеству;
- жёсткие ограничения подтверждены данными; неизвестное не считается выполненным.

Разделяем три вида основания: `qloo_affinity`, `shared_tags`, `editorial`. Последний — субъективное предложение порядка или атмосферы, не факт провайдера. Фактические пояснения лучше собирать серверными шаблонами; свободному тексту оставляем только явно редакционную часть. Проверка ID сама по себе не доказывает правдивость всех фраз модели.

Qloo описывает `feature.explainability=true` и относительные влияния входных сигналов. Сначала нужно проверить наличие и форму ответа на hackathon host для наших категорий. Такие значения не выдаём за вероятность симпатии или доказательство причинной связи. При отсутствии explainability говорим о совместном запросе по интересам, не приписываем результат конкретному любимому исполнителю. Источник: [Insights API Deep Dive](https://docs.qloo.com/reference/insights-api-deep-dive).

Pydantic AI позволяет проверять результат с доступом к контексту и вернуть `ModelRetry`; эту возможность используем для одной исправительной попытки. Невалидированный частичный ответ не показываем пользователю. Источник: [Output validators](https://pydantic.dev/docs/ai/core-concepts/output/#output-validators).

## Ограничения работы

Начальные значения для внедрения, не измеренные оптимальные настройки:

- максимум 4 обращения к модели, включая исправление;
- максимум 6 успешных вызовов инструментов;
- максимум 6 HTTP-попыток Qloo на весь запуск, включая ошибки и повторные попытки;
- не более одного исправления невалидного выхода;
- общий deadline 25 секунд, после которого сохраняется доступная фактическая подборка без агентного плана;
- максимум 12 сущностей в контексте планирования; описания обрезаются до ограниченной длины.

SDK-счётчик успешных инструментов не заменяет бюджет внешнего API. Отдельный счётчик резервирует попытку **до** сетевого обращения. Начальная загрузка интересов и любые запросы вне инструментов также входят в этот бюджет. Лимиты уровня приложения должны учитывать параллельные запросы и общую квоту, а не только один запуск.

В эксперименте зафиксирован Pydantic AI 1.107.7. Проверены `UsageLimits(request_limit, tool_calls_limit)` и собственный счётчик попыток. Публичная документация может описывать более новые API; параметры обновляем только вместе с тестами. Установку в backend проверяем отдельно: работа эксперимента не доказывает совместимость всех production-зависимостей.

Отмена локального ожидания не гарантирует, что провайдер остановил генерацию или не спишет оплату. Перед живым запуском нужны token limits, лимит запросов на сессию и квота аккаунта провайдера. Пока не подключаем внешнюю отправку полных traces: предпочтения человека и prompt не должны попадать в телеметрию без осознанного решения.

Описания сущностей и ввод пользователя считаем недоверенными данными. Инструкция внутри описания не даёт новых полномочий. Реальная защита — ограниченные инструменты и проверки на стороне Python, а не только фраза в системном prompt.

## Память

Источником вкусов остаются явные действия: исходные интересы, save, not_for_me, already_know. Не сохраняем предположения модели о личности, демографии или причинах вкуса как факты. Снимок плана хранится с версией prompt, модели, политики и evidence. Новый отзыв меняет следующую подборку, не переписывает историю.

На первом этапе не нужны векторная БД, бесконечная история чата или отдельный memory-agent. Короткое состояние запуска и несколько явных реакций уже дают проверяемый цикл адаптации.

## Что проверено сейчас

Отдельный эксперимент находится в `research/agent-spike`, не импортируется production-приложением. Использует сценарную `FunctionModel`, без LLM/Qloo ключей; реальные model requests запрещены настройкой тестов. На Python 3.12 прошли 11 тестов:

1. вызов инструмента и валидный структурированный ответ;
2. неизвестный ID с исправлением;
3. evidence другой сущности с исправлением;
4. дубли с исправлением;
5. отклонённая сущность с исправлением;
6. не полученная инструментом сущность с исправлением;
7. остановка после исчерпания исправлений;
8. запрет группы инструментов сверх лимита до побочных эффектов;
9. остановка цикла по количеству обращений к модели;
10. независимый бюджет попыток получения данных;
11. отмена ожидания сценарной модели по общему deadline.

Это подтверждает механизмы runtime, **не способность реальной модели выбрать нужный инструмент или хороший план**. Подход к сценарным тестам: [Pydantic AI Testing](https://pydantic.dev/docs/ai/guides/testing/). Альтернатива с аналогичной целью — [ScriptedModel в OpenAI Agents SDK](https://openai.github.io/openai-agents-python/testing/).

## Как проверим качество после ключей

Собрать минимум 20 фиксированных случаев: пересечение разных интересов, неоднозначное имя, sparse metadata, Safe/Wild, сильное исключение, противоречивое намерение, недоступная категория, instruction injection в данных. Для каждой конфигурации — минимум три повторения. Синтетические сценарии нужны для безопасности; качество рекомендаций проверяем на настоящих ответах Qloo.

Сравнить на одинаковых интересах и сохранённых исходных пулах:

1. Qloo + текущее ранжирование без агента;
2. тот же shortlist + агентное планирование;
3. полный агент с дополнительным поиском кандидатов.

Так видно отдельно пользу текста/плана и пользу дополнительных инструментов. Не сравниваем произвольные разные ответы провайдера как будто это чистый эффект агента.

Автоматические критерии: ноль неизвестных ID, ноль ссылок на чужое evidence, ноль нарушений подтверждаемых жёстких ограничений; доля валидных завершений, число ремонтов, запросы и стоимость. Для качества — слепая ручная оценка соответствия намерению, понятности основания и интересности плана. Полезность не поручаем оценивать исключительно другой LLM. p50/p95 задержки и цены измерим, а не назначим заранее.

Название модели пока не фиксируем. Сравним две доступные модели с structured output и tools на одном наборе. Выберем самую экономную, которая проходит критерии, вместо выбора по маркетинговым заявлениям.

## Следующие изменения

1. Вынести DiscoveryService и добавить общие бюджеты запросов.
2. Ввести `Intent`, `Evidence`, `AgentContext` и три варианта ответа; сохранить обратную совместимость текущего API.
3. Добавить Pydantic AI в backend и адаптировать эксперимент в интеграционные тесты с существующими ranking, QlooClient и сессиями.
4. Подключить три узких инструмента и серверную сборку пояснений. Без ключа режим явно недоступен; не заменять его демонстрационными рекомендациями.
5. После Qloo-ключа проверить explainability, реальные ответы и покрытия. После model-ключа выполнить evaluation и только затем включить агентный путь.

Основная работа ближайшего этапа — пункты 1–4. Интерфейс может пока оставаться простым: ценность проекта должна проявляться в проверяемом поведении агента.
